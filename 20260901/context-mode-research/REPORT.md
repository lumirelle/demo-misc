# context-mode 是否真的能节省上下文?——调研报告

- **调研对象**:https://github.com/mksglu/context-mode (npm: `context-mode`,v1.0.169)
- **调研日期**:2026-09-01
- **调研方式**:① 官方 README/BENCHMARK.md 文档分析;② 直接探测其 MCP 服务器实测固定开销;③ 在安装了 context-mode 的本会话内做 A/B 对照实验;④ 核验 GitHub issues 中的社区反馈;⑤ npm 下载量与许可证核查。

---

## TL;DR

**结论:能省,但有条件,且官方数字有美化。**

1. **机制真实有效**:工具输出在沙箱子进程处理、只回传摘要,本会话实测 140KB 数据只进上下文 ~300 字节,与官方声称一致。
2. **官方账本(91.2% 节省)偏乐观**:它不计入 **~7,400 tokens 的固定开销**(11 个工具 schema,每轮请求都要携带),漏计非 ctx 工具(bash)直出的内容,且 ctx_search 按"潜在可避免量"而非"实际避免量"记账。
3. **盈亏平衡点约在"单会话工具原始输出 > 35–40KB"**:日志分析、网页调研、测试输出、大文件处理等输出密集型任务能数倍回本;轻量会话(几个小命令、短编辑)是净亏损。
4. 社区 issue(#1031、#567、#1077)与本次实测相互印证:固定开销是真问题,个别平台下甚至"token 不降反升"。

## 1. 项目概况

| 项目 | 数据(2026-09-01) |
| --- | --- |
| GitHub | mksglu/context-mode,~20.3k stars,~1.5k forks,2,165 commits |
| npm | v1.0.169,近一周下载 17,960,近 30 天下载 78,501 |
| 许可证 | Elastic-2.0(BSL 类,**非** OSI 开源) |
| 形态 | MCP 服务器(11 个 `ctx_*` 工具)+ PreToolUse/PostToolUse/SessionStart hooks + 7 个 skills |
| 支持平台 | 宣称 17 个:Claude Code、Pi、Cursor、Codex、Gemini CLI、VS Code Copilot 等 |

**工作原理**:
- `ctx_execute` / `ctx_execute_file` / `ctx_batch_execute`:命令在沙箱子进程运行,**只有 stdout/摘要进入上下文**,原始字节留在沙箱内。
- `ctx_index` / `ctx_fetch_and_index`:文档/网页按标题切块存入 **SQLite FTS5**;`ctx_search` 用 BM25 + 词干化 + trigram + RRF 融合按需取片段。
- `ctx_stats` / `ctx_doctor` 等 5 个元工具:统计、诊断、升级、清空、仪表盘。
- Hooks:会话启动注入路由提示;拦截产生大输出的工具(如 bash 中的 curl)并引导改用 ctx 工具;PostToolUse 捕获决策/错误/阻塞等事件供后续检索。

## 2. 官方声称(BENCHMARK.md)

21 个场景,总原始数据 376KB → 上下文消耗 16.5KB,**总体节省 96%**。代表性场景:

| 场景 | 原始 | 进上下文 | 节省 |
| --- | --- | --- | --- |
| Playwright 页面快照 | 56.2 KB | 299 B | 99% |
| GitHub issues(react) | 58.9 KB | 1,139 B | 98% |
| 访问日志(500 请求) | 45.1 KB | 155 B | 100% |
| 分析 CSV(500 行) | 85.5 KB | 222 B | 100% |
| Git log(153 commits) | 11.6 KB | 107 B | 99% |
| **最差:网络请求(0.4KB)** | 0.4 KB | 349 B | **仅 13%** |
| **最差:Supabase 文档(3.9KB)** | 3.9 KB | 2,246 B | **仅 44%** |

宣传语:"30 分钟的会话延长到约 3 小时"。

## 3. 本次实测(在本会话内,A/B 对照)

### 3.1 固定开销:每会话 ~7.4K tokens 的"税"

通过 MCP JSON-RPC 握手直接探测其服务器的 `tools/list`,11 个工具 schema 总计 **29,690 字符 ≈ 7,400 tokens**(按 4 字符/token 估算):

```
ctx_execute 5,214 | ctx_execute_file 3,326 | ctx_index 3,352 | ctx_search 4,410
ctx_fetch_and_index 3,954 | ctx_batch_execute 4,596 | ctx_purge 2,552
ctx_stats 494 | ctx_doctor 504 | ctx_upgrade 582 | ctx_insight 706
```

之外还有:7 个 skill 描述(约 500+ tokens)、会话启动注入的 hook 提示、每次 ctx_search 结果尾部追加的节流提示。**关键点:工具 schema 属于请求级常量,每一轮对话都要重新发送**,长会话累计成本 = 7.4K × 轮数。

### 3.2 A/B 对照:机制有效

| 实验 | 数据量 | 进入上下文 |
| --- | --- | --- |
| 同一份 35KB JSON 日志,`bash cat` 直出(模拟无 context-mode) | 34,926 B | **全部 35KB**(本次调研为此付出了真实代价) |
| 同一份 140KB JSON 日志,`ctx_execute` 处理 | 139,977 B | **~300 B 摘要**(条数、分级统计、均值) |

机制本身与官方声称一致:沙箱处理 + 只回摘要,确实把 99.8% 的原始字节挡在上下文之外。

### 3.3 官方 ctx_stats 账本 vs 真实账本

ctx_stats 本会话显示:*"82.0K tokens saved · 91.2% reduction(without 351KB / with 31.0KB)"*。经逐项核对,发现三处记账偏差:

1. **漏计非 ctx 工具的直出**。实验中 bash 直出的 35KB 实际进入了上下文,但 "with context-mode" 柱只从 27.9KB 涨到 31.0KB(+3.1KB)——它只统计 ctx_* 工具自身的输出。
2. **不计固定开销**。~30KB 工具 schema + ~3KB skills/hooks 完全不进账本。
3. **ctx_search 按"潜在避免量"记账**。2 次 ctx_search 实际返回约 8KB 片段,却被记为 "137 KB saved"(索引源的全部原始大小)。这是"如果你不按需检索就会全量加载"的假想节省,不是实际发生的节省。

**本会话真实账本(重构)**:

```
真实上下文成本 ≈ 31KB(ctx 工具输出)
             + 35KB(bash 直出,官方漏计)
             + ~33KB(工具 schema + skills + hook 注入)
             ≈ 99KB
对照基线(若无 context-mode,做同样的调研) ≈ 290KB+(README 110KB + BENCHMARK 7KB + 实验数据 175KB)
净节省 ≈ 65%~70%(而非官方显示的 91.2%)
```

即便打折,本会话这种**输出密集型**调研的净节省依然显著;但固定开销占比已经很明显。

### 3.4 实测中发现的其他摩擦

- **跨平台问题**:Windows 上 `ctx_execute` 的 shell 语言走 PowerShell,bash 语法(heredoc、`||`)直接解析报错;失败重试本身也消耗上下文和轮次。
- **Hook 干扰**:bash 中的 curl 被拦截并注入引导文案;每次 ctx_search 附带节流提示(ctx_search 有 8 次/窗口的速率限制,重检索型工作流会被限速)。
- **编排轮次变多**:index→search 两步、多查询合并等模式比一次性读取多花 1–2 轮,每轮都重发全部历史 + 固定开销。

## 5. 盈亏平衡分析

**净收益 ≈ Σ(避免的原始输出 − 实际回传的摘要) − 固定开销(~8–9K tokens)− 额外编排轮次成本**

| 会话类型 | 原始输出总量 | 判定 |
| --- | --- | --- |
| 日志/测试输出分析、网页调研、大 CSV、Playwright 快照、codebase 统计 | 数百 KB | **数倍回本**,会话寿命显著延长 |
| 中等:带几条长命令输出的调试 | 50–150KB | 明显净赚 |
| 轻量:几个小 grep/短命令、纯代码编辑、问答 | < 35KB | **净亏损**(白付 ~8–9K token 固定税) |
| 小输出多轮交互(其最差场景:0.4KB 网络请求) | 极小 | 净亏损,节省率仅 13% |

注意两个放大效应:
- 固定开销**每轮重发**:20 轮的轻会话累计多付 ~150K tokens 的 schema 成本;
- 反向放大:原始输出一旦进入上下文也会**在后续每轮重发**——所以输出越大的会话,省下的复利越大。这正是"重会话回本、轻会话亏损"的根本原因。

## 6. 结论与建议

**"是否真的能节省上下文?"——是,但仅限于特定工作负载,且数字要打折扣看:**

1. ✅ **机制真实**:沙箱外置 + 按需检索在输出密集型任务上确实大幅减少进入上下文的字节,本会话实测与官方 benchmark 方向一致。
2. ⚠️ **官方节省率(91–96%)系统性高估**:不计固定开销、漏计非 ctx 工具直出、按潜在量而非实际量记账。真实净节省视负载约在 50–90% 之间,轻会话为负。
3. ⚠️ **~7.4K tokens 固定税是真实成本**(其自家 issue #1031 也承认 ~6.2K),工具描述 80% 是引导性文字,可精简但官方未做。
4. 💡 **建议**:
   - 输出密集型工作流(调试长日志、跑测试、网页/文档调研、数据分析)**值得开启**;
   - 轻量问答、小编辑为主的项目**不必开启**,或仅在需要时按项目启用;
   - 不要把 ctx_stats 的百分比当作真实节省,它更接近"最优情况上界";
   - Windows 用户注意 shell 语言走 PowerShell 的坑;依赖 Node ≥ 22.5 或带 better-sqlite3 原生构建,安装失败时会静默失去收益(参见 issue #567)。
