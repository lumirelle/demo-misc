Reorder & drop commits

Reordering history is one command, not an interactive-rebase staring contest — and the descendants follow automatically.

In Git, reordering commits means opening git rebase -i, editing a todo list, and hoping the whole thing doesn't collapse into conflicts. In jj, a commit's position is just metadata, and you move it with a single command addressed by revset.

The one idea

You already know from Lesson 2 that rewriting a commit auto-rebases its descendants. Reordering is just a special case: moving a commit to a new parent. jj rebases the moved commit, then re-stacks everything else for you.

The command is jj rebase, and you pick the commit by revset, not by "the current branch" — there is no current branch. Two flags do the moving:

Move a commit 
jj rebase -r <rev> -A <dest>
   place <rev> right after <dest>

jj rebase -r <rev> -B <dest>
   place <rev> right before <dest>
Move a stack 
jj rebase -s <rev> -o <dest>
   move <rev> and all its
   descendants onto <dest>

And to delete a commit entirely, there's jj abandon — jj's "drop", which rebases the descendants onto the abandoned commit's parent.

Do it now

Build a three-commit stack. (Change IDs on your machine will differ.)

jj git init reorder-demo
cd reorder-demo
echo "a" > a.txt; jj describe -m "add a.txt"; jj new
echo "b" > b.txt; jj describe -m "add b.txt"; jj new
echo "c" > c.txt; jj describe -m "add c.txt"; jj new

Top-to-bottom:

@  ulosmsyw  (empty) (no description set)
○  lrvxyxnt  add c.txt
○  wtytlksy  add b.txt
○  tykzqmxx  add a.txt
◆  zzzzzzzz  root()

The revsets @-, @--, @--- mean "parent", "grandparent", "great-grandparent" of the working copy — so @--- is the add a.txt commit.

  1. Move the bottom commit to the top. 
    jj rebase -r @--- -A @-
    Rebased 1 commits to destination.
Rebased 3 descendant commits.
Working copy  (@) now at: soroxqux 1a4a9bb1 (empty) (no description set)
Parent commit (@-)      : tykzqmxx 21f60b22 add a.txt

    Read that: it rebased the one commit you asked about (add a.txt), then automatically rebased its three descendants. The stack is now add b.txt → add c.txt → add a.txt.

    @  soroxqux  (empty) (no description set)
○  tykzqmxx  add a.txt      ← moved to top
○  lrvxyxnt  add c.txt
○  wtytlksy  add b.txt
◆  zzzzzzzz  root()

    Same change IDs, new order. Compare that to three steps of git rebase -i.

  2. Drop a commit. Abandon the add b.txt commit (now @--). 
    jj abandon @--
    Abandoned 1 commits:
  wtytlksy 28f1abff add b.txt
Rebased 2 descendant commits onto parents of abandoned commits.
Added 0 files, modified 0 files, removed 1 files

    jj abandon deletes the commit and re-stacks its descendants onto its parent. The b.txt file it introduced is removed along with it.

  3. Undo both, if you like. 
    jj undo   # restore the abandoned commit
jj undo   # back to the original order

    Same safety net as Lesson 2 — nothing you do while rearranging history is irreversible.

What you just did

You reordered a commit and dropped another — the two operations that in Git send you into rebase -i's todo list and reflog recovery. In jj each was one command, addressed by revset, with the descendants handled for you and jj undo always available.

The revset vocabulary so far

@ working copy · @- parent · @-- grandparent · @--- great-grandparent. These are how you point at commits; there's no "HEAD" and no branch name to remember.
