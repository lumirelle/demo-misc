Jujutsu · Lesson 0001

The working copy is a commit

The one idea that makes jj feel completely different from Git — and your first commits in it.

You're here to replace Git as your daily driver. Every mental model you have from Git — the index, the branch, the dirty working tree — is about to be challenged by a single fact: in jj, your working copy is a commit.

The one idea

In Git, your edits live in three places that you shuttle between by hand: the working tree, the index (staging area), and commits. You edit, then git add, then git commit. Until you commit, your changes are only half-saved, and Git will happily warn you that your working tree is dirty.

jj collapses this. There is no explicit index or staging area. Every time you run a jj command, it snapshots your working copy into a real commit automatically. The working copy is simply the commit marked @ — the one currently checked out. Nothing is ever "unstaged" or "dirty"; it's just a commit you haven't named yet.

Git — you drive the index

Changes sit in limbo until you stage and commit them by hand.

vim notes.txt
git add notes.txt      ← stage it
git commit -m "msg"    ← now saved
git status             ← am I clean?
jj — saved instantly

Your edit is already a commit. You only give it a message.

vim notes.txt
jj st                  ← already recorded
jj describe -m "msg"   ← just name it
jj log                 ← history, with @
Why this matters for the mission

This one change removes the source of Git's most common daily friction: "your local changes would be overwritten", forgotten git adds, and the reflex to git stash. jj subsumes both the index and stashes into a single, simpler object.

Do it now

First, one-time setup. jj keeps its own identity config — it does not read your Git user.name/user.email. Without it your commits get an empty identity and can't be pushed. Set it once:

jj config set --user user.name  "Your Name"
jj config set --user user.email "you@example.com"

Now open a terminal and follow along. (Change IDs and hashes in the output below will differ on your machine — that's expected.)

  1. Create a repo. 
    jj git init my-first-jj
cd my-first-jj

    jj git init creates a Git-backed repo, colocated with a .git dir by default, so plain git still works here too. You'll see Initialized repo in "my-first-jj".

  2. Look at the status. 
    jj st
    The working copy has no changes.
Working copy  (@) : zuryntwn 4fa33b2b (empty) (no description set)
Parent commit (@-): zzzzzzzz 00000000 (empty) (no description set)

    There's already a working-copy commit (@) sitting on top of a parent. It's (empty) — a commit with no changes yet. Notice there's no git init style "branch" to create; you're already on a commit.

  3. Edit a file — and do nothing else. 
    echo "hello" > notes.txt
jj st
    Working copy changes:
A notes.txt
Working copy  (@) : wssrxtwy 1aae205b (no description set)
Parent commit (@-): zzzzzzzz 00000000 (empty) (no description set)

    No add, no staging. The change is already in the working-copy commit. Watch what jj diff says:

    jj diff
    Added regular file notes.txt:
        1: hello
  4. Name the commit. 
    jj describe -m "add notes.txt"
    Working copy  (@) now at: wssrxtwy f2a3b8cb add notes.txt
Parent commit (@-)      : zzzzzzzz 00000000 (empty) (no description set)

    jj describe is how you write a commit message — think of it as git commit -m, except the changes were already committed. Notice something subtle: the change ID stayed wssrxtwy but the commit ID changed (1aae205b → f2a3b8cb). We'll return to this.

  5. Start the next commit and read the log. 
    jj new
jj log
    @  ollrkkox (no email set) 2026-09-21 13:56:45 9b0185e2
│  (empty) (no description set)
○  wssrxtwy (no email set) 2026-09-21 13:56:45 f2a3b8cb
│  add notes.txt
◆  zzzzzzzz root() 00000000

    jj new starts a fresh, empty commit for your next change — the jj answer to "make a new commit on top." The log reads top-to-bottom like a timeline: @ is your working copy, ○ is an ordinary commit, ◆ is the immutable root.

What you just did

You created a repo, made a change that was automatically committed, gave it a message, and started the next commit — all without a single git add, git commit, or git status. The workflow is: edit → describe → new → repeat.

That wssrxtwy/f2a3b8cb split you noticed is jj's two identifiers:

  • Change ID (wssrxtwy): stable identity for a logical change. It survives rewriting.
  • Commit ID (f2a3b8cb): content hash, like a Git SHA. It changes whenever the commit is rewritten.

In Git, a commit is its hash — rewrite it and it's a brand-new thing. In jj, a change keeps its identity while its content evolves. That's the foundation for the easy history-rewriting you came here for; we'll build on it next lesson.
